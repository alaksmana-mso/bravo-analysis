1. Problem statement

Bravo's loan origination service (ms-bpm, repository bravo-bpm-service) runs Camunda 7.23.0 Community Edition embedded in Spring Boot 3.5.16. Both are out of support. Camunda 7 Community ended on 14 October 2025 and will never get another patch. Spring Boot 3.5 open-source support ended on 30 June 2026.

On top of that, the production engine holds 61 injected remote-code-execution process definitions. One of them ran. So Bravo is an unpatchable engine with confirmed code execution in production, carrying about 118,000 applications a month and the majority of BFI's origination value (≈Rp50.2bn against LORA's ≈Rp2.4bn).

Two things have to happen:

  1. Harden what we have, now. Fix the credential and configuration problems that let the definitions in. This is owed under every option and does not wait for a platform decision.
  2. Choose a platform response. Stay on the Camunda lineage (Option 1, in three variants), move to Temporal (Option 2), or move to LORA (Option 3). This page sets out the pros and cons. The CTO decides, on cost and effort.

The decision criteria agreed for this page: cost, effort, x-factor, and whether it mitigates the security finding.

2. Security finding: Camunda RCE on production BPM

Severity: Critical. Confirmed code execution inside the production ms-bpm pod, on an engine with no patch channel. Full write-up: SECURITY-FINDING-camunda-rce.md.

2.1 What was found

  • The Camunda engine behind prod-ms-bpm contains 61 process definitions that are not part of the application. They were deployed between 2026-05-23 02:50 and 2026-06-30 13:08, in 7 distinct sessions.
  • They are textbook Camunda expression-injection probes. Examples: prod_rce_bypass builds java.lang.Runtime by reflection through string concat() and runs hostname; cmd_sh_c runs sh -c uname; cmd_id, direct_ls, direct_cat, direct_ps are OS command probes; kw_getRuntime, meta_forName and others map which reflection primitives the engine allows; nine x1_* definitions are full RCE payloads.
  • All 61 are still active (suspension_state_ = 1). They can be started today.

2.2 Proof it executed

Deploying a definition does not run its expression. Starting an instance does. Exactly one probe instance was ever started: process x1_1781161729, started 2026-06-11 07:08:51, completed 14 ms later. Its captured result variable holds prod-ms-bpm-75765895b4-dxbq4, the Kubernetes pod hostname. That is command output from inside the production JVM, written into the Camunda history tables. Code execution is confirmed by data, not inferred from configuration.

2.3 How it was possible (corrected 2026-09-10)

The finding was first published as "unauthenticated RCE". The Bravo team pointed out that a caller must be registered in Keycloak. They were right, and the mechanism was corrected:

PointOriginal claimVerified
Deploy vector/camunda/** is permitAll(), so anyone can deployThe deploy path is POST /engine-rest/deployment/create. It does not match /camunda/**, so it falls through to authenticated() and requires a credential.
permitAll() on /camunda/**The holeReal, but it exposes the Cockpit webapp, which has its own login and cannot deploy. Hardening, not the breach.
Null start_user_id_ means unauthenticatedAssertedWithdrawn. The shared-secret path sets no Camunda identity, so this is null for ordinary traffic too.

Two credentials satisfy the deploy path, both via InternalAuthenticationFilter: a Keycloak user token, or the shared internal service secret (api-secret: <INTERNAL_SERVICE_KEY>), which grants ROLE_SYSTEM_SERVICE.

The corrected finding is worse in one way. Whoever deployed those definitions held a valid BFI credential. This is an insider, an authorised tester, or a leaked secret. Two aggravating facts:

  1. INTERNAL_SERVICE_KEY is a single static shared value, compared with .equals(). Not per caller, not rotated, not scoped.
  2. Once past Spring, the caller has full engine rights. No ProcessEngineAuthenticationFilter is registered on the REST API, so no Camunda identity is set, and Camunda skips authorisation when no identity is set. camunda.bpm.authorization.enabled: true does nothing on this path.

So INTERNAL_SERVICE_KEY is an RCE-equivalent credential. That is a design issue and it stands independently of this intrusion. A plausible source: bravo-e2e-test/cypress.config.js carries committed plaintext credentials across 600 commits and 46 contributors. Whether one of those was used is not established.

Still unverified: whether /engine-rest/** is reachable from outside the cluster. The repository holds no Ingress manifest. Datadog confirms the webapp paths are reachable; it does not establish the same for the REST API. The engine recorded nothing about who did this (act_hi_op_log is empty for these deployments), so attribution has to come from HTTP access logs.

2.4 Blast radius

  • Confirmed: arbitrary OS command execution as the ms-bpm process user inside the production pod.
  • Reachable from there: the SPRING_DATASOURCE_* credentials (full read and write on application, loan, customer and Camunda history data), the Datadog agent, the GKE service-account token and metadata endpoint, and every internal service the pod can call.
  • Scope: conventional BPM production only. The Sharia engine was checked and is clean.

Why it is reachable. Who legitimately uses it from outside. Nobody. Datadog APM shows zero requests to /engine-rest for prod-ms-bpm since 4 July 2026, any method (section 2.6). The nine in-cluster callers use the application's own /bpm/v1/** endpoints, and operators use Cockpit's own API under /bpm/camunda/api/….

Scope, to avoid a misreading: PR 14169 does not make BPM private. It denies one path prefix, /bpm/engine-rest/**, for requests arriving through the nginx ingress controllers. Every path the public front ends call today, /bpm/v1/**, /bpm/v2/**, /bpm/v3/** and Cockpit under /bpm/camunda/**, keeps being served over the public ingress exactly as now. Browser RUM for the last 7 days: about 13 million calls to microservices.prod.bravo.bfi.co.id/bpm/v1|v2|v3/…, zero to /bpm/engine-rest. The team is right that BPM cannot be made private today, because the consoles call it directly rather than through the Krakend public gateway; that is a separate, later programme (route the consoles through Krakend first, then move the /bpm Ingress to the private class). This policy does not depend on it and stays valid after it.

The fix: restrict to cluster-internal

PR 14169 adds bpm/templates/engine-rest-authorization-policy.yaml, an Istio AuthorizationPolicy with action: DENY on the bpm pods (app: ms-bpm, or bpm-sharia for Sharia). It denies /bpm/engine-rest and /bpm/engine-rest/* when the request's source namespace is nginx-ingress, which is where both the public and the private controller run. In-cluster services are not matched. It is enabled in all six environments (prod, prod-sharia, sit, sit-sharia, uat, uat-sharia) through engineRestPolicy in the values files, and rendered with helm template for each.

  • Why Istio and not nginx. One object covers both ingress controllers and is enforced at the pod, so it holds even if another Ingress appears. Source identity is trustworthy because traffic from both controllers to ms-bpm is mutual TLS (Istio connection_security_policy:mutual_tls; principals spiffe://cluster.local/ns/nginx-ingress/sa/nginx-ingress-protected and …/sa/prod-nginx-ingres-private). The repo already uses this pattern (krakend internal gateway, agreement circuit breaker). An nginx snippet is blocked by ingress-nginx's default annotation word blocklist, which rejects location.
  • Rollout. ArgoCD sync SIT, then UAT, then prod. After each: the external GET returns 403 (Envoy "RBAC: access denied") instead of 401; an in-mesh GET from an ms-onboarding pod still returns 401; Cockpit and /bpm/v1/** unchanged.
  • Rollback. engineRestPolicy.enabled: false or revert. The policy is additive.
  • Caveats. SIT and UAT Sharia pod labels are inferred from prod telemetry; a wrong label means the policy selects nothing and has no effect, so it cannot cause an outage. Istio path matching is literal after normalisation: if the mesh is not at least on MERGE_SLASHES normalisation, /bpm//engine-rest/… could slip past; bravo-terraform sets no explicit pathNormalization, so that is a recommended follow-up there.
  • Not in this PR. Action 9 (Cockpit behind the private ingress only) can reuse the same template with a second rule scoped to the protected controller's principal. The application-side fixes (per-caller credentials, ProcessEngineAuthenticationFilter) remain owed in bravo-bpm-service.

3. Options

The hard constraint behind all of them: Camunda 7.23's Spring Boot starter will not run on Spring Boot 4. So moving to a supported Spring Boot forces an engine decision. "Upgrade Spring Boot first and decide about Camunda later" is not available.

Option 1: stay on the Camunda 7 lineage

Keep the engine family, the ACT_ schema, the 53 BPMN files and the 272 delegates. Change who maintains the engine. Three variants. In all three, Java 17 stays, no data migrates, and rollback is "redeploy the previous artifact against the same database".

Option 1a: Camunda 7 Enterprise Edition

Replace the 7.23.0 Community artifacts with Camunda's Enterprise artifacts at the current EE minor, from Camunda's private Maven repository, with a licence key in configuration. Same package names, same schema, same Cockpit plugins. No code rename is needed. (Camunda 8 is a different programme: it removes the embedded engine and drops the ACT_ tables. It is not what this option buys, although the quote prices it the same.)

Pros. A contract with the company that wrote the engine. CVE fixes from the original maintainers. A published support calendar: full support to 13 April 2030, extended support to April 2032, environment updates every April and October. No 7.24 hop, no bundle relocation, no package rename.

Option 1b: Operaton

Apache 2.0 community fork of Camunda 7. Engine 2.1.4 on Spring Boot 4.0.8. Keeps the ACT_ schema, accepts the legacy camunda: BPMN namespace, ships an automated OpenRewrite migration recipe. Requires a 7.24 hop first (one schema-log row, no DDL).

  • Effort: 20–33 engineer-days, one engineer, one regression cycle. ≈Rp45–125M one-off. No licence. Run-rate unchanged at ≈Rp58M a month.
  • Pros: the healthiest fork by a wide margin: 2,310 commits in 52 weeks against CIB seven's 258, 52 distinct authors against 31, pure Apache 2.0 with no paid tier. Lands on a supported engine and a supported Spring Boot in one change.
  • Cons: no legal entity yet (non-profit planned); six-month support lines; ~80% of commits from one contributor; no support contract on offer. Five concrete migration frictions: the 7.24 hop, a missing CollectionUtil class (2 files), seven Cockpit plugin bundles to relocate, two missing test dependencies, loss of BPMN path-coverage reports on 4 tests.
  • Mitigates the security finding? Same as 1a: patch channel yes, BFI configuration no.
  • X-factor: this is a chosen dependency on a small project, and it will be scrutinised differently from the drift that put Bravo on an end-of-life engine.

Option 1c: CIB seven

Apache 2.0 fork maintained by CIB software GmbH (Munich). Engine 2.2.0 on Spring Boot 4.0.6, released 31 May 2026. Same schema and namespace guarantees as Operaton. No 7.24 hop needed.

  • Effort: 18–30 engineer-days, one engineer, one regression cycle. ≈Rp45–125M one-off. No licence. Run-rate unchanged.
  • Pros: the cheapest migration: avoids all five Operaton frictions. Two ex-Camunda core engineers on staff. Paid long-term support is purchasable. Cockpit plugin paths unchanged.
  • Cons: smaller project (258 commits, 31 authors in 12 months). Support terms are not published: length, service levels and price are sales-contact only.
  • Mitigates the security finding? Same as 1a and 1b.
  • X-factor: a chosen dependency on one Munich company. If a support contract is wanted, start that enquiry before choosing, not after.

Common to 1a, 1b and 1c: the Spring Boot 4 upgrade (12–20 days: 308 @MockBean sites, Hibernate 6→7, ShedLock, removing the spring-framework-bom pin) is the larger half and is owed under Option 2 too. The one real database risk is schema-log drift: two Flyway migrations hand-replayed Camunda's 7.21 and 7.22 DDL, so ACT_GE_SCHEMA_LOG may be below the columns that exist. Diagnose per environment before setting a date. Rehearse on a PROD clone. The three operator consoles (763k lines, 829 tests) have zero Camunda references and need no change.

Option 2: Temporal, same paradigm

Port the ~60 BPMN definitions to imperative Temporal Java workflow code. The 225 JavaDelegate classes become Activities. The other 99.6% of the service, including the 238 JPA entities, 113 Feign clients and 217k lines of human-task code, does not move. BFI already runs Temporal Cloud (≈Rp140M a month, contracted March 2026).

  • Effort: pending Temporal’s assessment. An information package was sent to Temporal on 2026-10-02: the BPMN element inventory mapped to Temporal constructs, the engine coupling, the production footprint, BFI’s existing Temporal footprint, and twelve assessment questions including the three sequencing options and the in-flight strategy. A written assessment is expected in about four weeks. Our own estimate, to be replaced by theirs: 31–57 engineer-months, 12–18 months elapsed, 5–8 engineers, Rp930M–2.85B one-off; or an 8–14 engineer-month DF4W-only pilot on 5.5% of volume with an exit. The Spring Boot 4 half (12–20 days) is still owed on top.
  • Licence / run-rate: none new. Roughly neutral: +Rp4.5–12M a month in Temporal Actions, probably inside the existing commitment, minus the Camunda history load on Cloud SQL.
  • Pros: removes the workflow-engine vendor dependency for good. Same language, same mental model, no retraining. Only 2,004 of 497,970 lines touch an engine API. No data migration. Testable orchestration for the first time. Removes the Camunda REST and Cockpit attack surface entirely.
  • Cons: 20–40× the cost of Option 1 for the same end-of-support outcome. 384 escalation and link events have no Temporal equivalent and each is a design decision. Cockpit is a real operational loss. Camunda instances cannot be migrated, so both engines run for 6–12 months and a parked-instance tail never drains on its own. Value depends on Bravo having a 5–10 year life.
  • Mitigates the security finding? Yes, structurally, but only after cutover. Section 2.5 is required in the meantime.
  • X-factor: both BFI origination platforms end up on one vendor.

Option 3: LORA

Close LORA's product coverage gap, prove parity, move the remaining Bravo book over, and switch Bravo off. LORA runs Go and a data-centric GSM planner on Temporal Cloud. It carries one live product family today (NDF2W + NDF4W, via the partnership door).

  • Effort: 30–57 engineer-months, 15–24 months elapsed. Rp900M–2.85B one-off. The NDF2W monolith alone is 248,682 starts per 90 days and 16 master configs.
  • Licence / run-rate: none new. Retires ≈Rp58M a month in production, Rp70–100M with non-production. But the shared data plane LORA also calls stays, and per application LORA costs 5–6.5× more today.
  • Pros: the only option that ends with one platform and one team. Buys the validated GSM capability: add an automated step with no orchestration edit. Product isolation and in-flight deploy safety by construction. One span per activity, carrying the loan id.
  • Cons: a paradigm change, not just a runtime change. Merges two squads that ship independently today (BLCS and LN) into a shared-document model with no seam to split them back. LORA's own measured reliability gap (uncapped retries, ~half of loans never terminate) at 3× its current volume. Longest time on the unpatched engine. Nothing of Bravo's Java transfers.
  • Mitigates the security finding? Yes, by removing Bravo, after 15–24 months. Section 2.5 is required in the meantime.
  • X-factor: Bravo's ≈Rp50.2bn book moves onto the platform carrying ≈Rp2.4bn.

How to read it. The three Option 1 variants are the same engineering job and differ almost entirely in run-rate and in who stands behind the engine. Options 2 and 3 are a different cost class and a different timeline, and they are the only two that eventually remove the Camunda attack surface rather than patch it. None of the five replaces the hardening in section 2.5.
