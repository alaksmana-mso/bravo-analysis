Context

The "Bravo & Lora Billing" sheet (1-6wUnoxlFMYAs1Ik3QPDvp2gx7xr7oR3sLoBHpT-tHw) was a quick, hand-built estimate. It has four known problems:

  1. Wrong split. "Bravo" = everything in bravo-project not labelled LORA. Most of that is the shared data plane that LORA also calls. The Bravo team objected on 9 Sep, and the objection was upheld.

  2. Wrong counts. Bravo's August uses 76,446; the correct figure is 118,253 (reproduced 25 Sep from public.application). LORA's 171,479 and June's 2,789 are replaced by the LPW workflow count from Temporal.

  4. Missing costs. Datadog and Coralogix are on the GCP bill but outside bravo-project. Codacy and Snyk are not on it at all.

The goal is a Looker Studio page that refreshes itself each month and shows the seven figures you asked for, split the fair way.

How Shared is split: by share of applications. Each month:

  • Bravo share = Bravo applications ÷ (Bravo + LORA applications). LORA share = 1 − Bravo share.

  • Bravo's part of Shared = Shared × Bravo share. The same applies to LORA.

Cost per application (the headline figure) = (platform's orchestration cost + its part of Shared) ÷ its applications.

Worked example with August-like numbers: 118k Bravo and 135k LORA gives Bravo 47% and LORA 53%. So 47% of Shared goes to Bravo and 53% to LORA.

Because the split follows volume, the Shared part costs the same per application on both platforms. The whole difference between Bravo and LORA then comes from the orchestration tier. The report shows this with a stacked bar per platform (orchestration + Shared part).

A tier-only figure (orchestration cost ÷ applications) is also shown, as a smaller line under each headline.

Plan: LORA counts from ArangoDB, and LPW workflows for the Shared split

Context

Today the "BFI Unit economics" sheet (1Kk2N0s20QnNHRMjQPeZ8bh5tYjgKc0qrxHU4B-P_8z0, built by bravo-analysis/tools/unit_economics_sheet.py) counts LORA applications as Temporal's "Workflows" actions ÷ 2. The LORA team says ArangoDB gives the accurate application count. You also want to keep the LPW workflow count, for two reasons:

  • it shows how much re-processing happens;

  • it measures how much of the Shared platform LORA actually uses.

What the code says (read-only investigation, 27 Sep):

  • Every LORA application is one document in prod ArangoDB, database partnership-ndf-v2, collection doc_pending (lora-process-sdk/framework/runtime/db_store.go:19-23). Documents are never deleted, so all history back to launch is there. That covers Jan–Mar 2026, which Temporal cannot give.

  • The document _key is the LPW workflow ID (the application UUID, lora-process-sdk/framework/runtime/workflow.go:277). One LPW workflow = one document, and the gateway refuses to reuse an ID (lora-gateway-service/.../application/start.go:105).

  • Where re-processing shows up:

    • Started but never verified: the document exists, but data.submission_date is empty.

    • Force-cancel and re-origination by IT Production: the old workflow is terminated and the loan restarted with a new UUID, giving a new document and a new LPW (1,269 tickets Jan–Aug, cost.md:1107-1143).

    • Rewind (Temporal reset): a new run of the same workflow, with the same document. It shows in Temporal runs only (705 in Jan–Aug, cost.md:1095-1102).

  • Useful fields:

    • version.created_at: the LPW start time.

    • data.submission_date: set by submission_verification, together with status new (scoring/submissionverification/impl.go:107-116).

    • data.loan_structure.product_id: 1 = NDF4W, 2 = NDF2W.

    • data.status.application and data.customer.ktp.nik.

  • No indexes exist on doc_pending, so each query scans the whole collection. Run it off-peak and return only the counts.

Decisions (you, 27 Sep):

  • LORA application = a document with submission_date set (a verified submission). This is the cost-per-application denominator.

  • Access: a read-only ArangoDB user for me, so I pull the numbers myself each month.

  • Carried over: UTC calendar months; Bravo count = the Bravo team's query 2.

Why cost per loan over-predicts. From Feb to Aug, loans grew 32% but cost grew only 8.8%. Cost per loan fell from Rp14,033 to Rp11,565, because most of the cost is fixed. Plan: Making unit economics permanent on GCP (2 Oct 2026)

Context

Today cost per loan lives in one private Google Sheet. It is rebuilt by a script on one laptop from spreadsheets that Finance shares by hand: SMS, Yellow.ai, EKYC and the IT budget. The FinOps service it reads from was down on 30 Sep, and the input files were once lost when the laptop cleared its temporary folder. That works for a first answer, but it does not last. This plan is how Finance, IT and the CTO can get the same numbers every month, permanently, on GCP.

Short answer: BFI does not need to buy a new tool. The three pieces already exist: the GCP billing data in BigQuery, the data team's dbt and lakehouse setup, and Google Workspace. They need to be connected. Finance keeps using Google Sheets, but only to enter what a machine cannot know: invoices, contracts and allocation keys.

How the data flows

Costs and volumes arrive by themselves. People enter only invoices, contracts and allocation keys. Nothing reaches a dashboard until the checks pass.

What each part does

  1. One home for the numbers: BigQuery. The billing data is already there, so costs need no new pipeline. SRE creates the dataset unit_economics and two service accounts, using the checklist already on the SRE to do page (items A to I).

  2. Finance keeps Sheets, as inputs. One Sheet each for contracts and licences, vendor invoices (SMS, WhatsApp, EKYC, credit bureaus) and allocation keys, kept in a shared drive rather than a personal drive. Each Sheet is linked to BigQuery as an external table, so typing in an invoice updates the dashboard. An AppSheet form can check each entry: month, vendor, amount, and whether VAT is included. Later, invoices can come straight from the accounts-payable system.

  3. The rules live in dbt, in Git. The cost buckets, the shared-cost split, cost per unique loan, re-processing cost and the vendor shares become dbt models. Today's Checks tab becomes dbt tests, so a wrong month fails loudly. The definitions go into the metrics layer and DataHub, so every team uses the same meaning of "cost per loan".

  4. Loan counts come from the source. Bravo counts come from the lakehouse, which already loads BPM. LORA counts come from a small Cloud Run job that reads ArangoDB read-only (the same query as lora_arango_counts.py), started by Cloud Scheduler on the 1st of each month.

  5. Each audience gets its own view. Looker Studio dashboards for the CTO and the teams, with the same charts as today's CTO view tab. Connected Sheets for Finance, so they can work with the BigQuery numbers inside Google Sheets and keep the Budget 2027 scenarios there. Later, BigQuery's built-in forecasting (ARIMA_PLUS) can draw the projection and flag unusual months.

  6. Costs are traceable at the source. This is what made the work hard so far.

    • Every GCP resource carries squad, app, env and cost-center labels, enforced in Terraform (bravo-terraform) and by an org policy.

    • Each vendor gets one API key or client ID per product, as Vonage already does, with invoices broken down by key.

    • The KYC proxy and the notification service record which product made each call. Today about half of the EKYC calls cannot be attributed.

    • Datadog tags (service, env, team) are kept consistent.

  7. Process and ownership. One owner (IT Finance or FinOps) and a monthly close, for example by working day 5. Closed months are frozen. Allocation keys are approved by the CTO and Finance and kept in one register. Each cost line maps to its IT budget code (ITOPxxxx), so the budget and the actuals line up.

The monthly routine

Who does what, and when. The working-day targets are suggestions for the owner to confirm.

Closed months are frozen. A later correction needs a short note, so last month's numbers do not change silently.

Ongoing

Running cost is small: a few gigabytes in BigQuery, free Looker Studio, and one short Cloud Run job a month. The paid Looker product (with LookML) only becomes worth it if many teams need governed self-service beyond what dbt and Looker Studio give.

Beyond Bravo and LORA

The same setup works for any part of the company that has a cost and a unit of work. Each one adds its own volume table and its own labels; the rest stays the same.

  • CONFINS: cost per active account.

  • Collection: cost per case.

  • Customer Care: cost per contact.
