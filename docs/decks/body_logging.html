01/Orientation

What was put in front of you, and what we did about it

One line in the platform decision deck asked for approval. We went and measured it against the billing data, the production logs and all 152 repositories.

The claim, as written

“Approve the Cloud Logging fix. It saves Rp 50–90M a month and is configuration only. That is more than retiring Bravo’s workflow tier would save.”

The mechanism named was loggerLevel: full on Feign, which makes every upstream call log its full request and response body.

What we checked

FinOps billing for August 2026, complete month, by project, service and SKU. Datadog production logs, two days, every service. All 152 repositories under squads/, pulled to master on the day of writing — 149,729 files scanned.

What came back

The direction is right and the prize is bigger than claimed. But three of the supporting facts do not survive contact with the data, and the fix that was named is not the one that pays.

We also found a live API credential sitting in production logs, which nobody was looking for.

A CTO should not be asked to approve a number that cannot be traced to a measurement. Three of these now can, and one still cannot.

04/The correction

The fix that was named cannot be shown to be doing anything

This is the part that should not go to a board without being settled. It takes one hour.

What the code says — the claim is real in the source

In bravo-bpm-service, application.yaml sets loggerLevel: full on 129 Feign entries including the default, and puts com.bfi.bravo.adapter at DEBUG. All 57 Feign clients live under that package. application-prod.yaml sets root: INFO but never overrides it — different keys in Spring Boot, so DEBUG survives.

On paper, every call to PEFINDO, SLIK, Dukcapil and CONFINS logs its full body.

What production says — nothing

Across two days, every production service:

Logs at status:debug — 0.
Logs containing END HTTP, the marker Feign writes at the end of every full-logged exchange — 0.

Two explanations, and we cannot tell which

1. A deployment environment variable overrides the log level. None of the 152 repositories contains a deployment manifest — they live in a GitOps repo we do not have. This is the likelier one.

2. Datadog drops DEBUG before indexing, and Cloud Logging still pays for it.
The ask

Read the ms-bpm deployment manifest. One hour. It decides whether this fix is worth Rp 0 or Rp 40M a month.

Until that is done, the Rp 50–90M figure is a code reading with no production signal behind it. It should not be quoted as settled.

The configuration is still wrong, whatever the answer

A default of full means one environment variable — or one careless merge — starts writing customer credit-bureau payloads into logs. That is a data-protection exposure sitting behind a single line. Six repositories carry it. Fix it regardless of whether it is currently costing money.

05/What is actually happening

Five services produce 64% of every log line we pay for

Measured in production, not read from code. Almost none of it is telemetry anyone reads.

confins-prod-ms-lms-ar-be2,640,74729%Genuinely blank log lines. Empty message field, several a second, 9.25 million a week. Shipped, indexed and stored. This service has no identified owner.
prod-lora-task1,291,27414%3.8 million warnings a week. A browser tab closing. An optional form field being absent. Nobody will ever act on any of it.
prod-ms-calculation770,3949%The entire HTTP error object serialised on every 4xx — roughly 12,000 a day. See the next slide.
prod-ms-cnv752,5628%The same error 20,000 times a day. Employee access records failing to sync and being discarded. A real defect nobody noticed, because it is buried in the noise.
prod-ms-bpm387,3324%Split JSON fragments and stack traces logged one frame per entry.
Top five of 71 services5,842,30964%

The discovery that explains the rest

The container runtime splits any log line over 16 KB into separate chunks, which arrive as unrelated entries. Neither half is valid JSON, so neither parses.

93.6% of our production logs cannot be parsed at all — 8.46 million of 9.03 million over two days. Large log lines are not just expensive. They are destroying the log pipeline.

Why this matters more than the Feign question

These five are measured, owned and fixable. Between them they are worth more than the disputed fix, and the ms-cnv item is a correctness defect — 20,000 employee access updates a day are being thrown away, possibly including role revocations.

No monitor noticed, because no monitor watches an outcome.

06/What is actually happening

A live API credential is being written to production logs

Found while measuring cost. It is not a cost item and it should not wait for this programme.

One line, in one file

lms-calculation-service/src/helpers/HttpHelper.ts:27 runs JSON.stringify(error) on every failed HTTP call and logs the result.

On an Axios error that serialises the entire request config — headers and body included.

What is in each entry, confirmed in production

— the api-secret header in plaintext, in full, on every 4xx or 5xx
— the request body, including customer birth_date
— the full stack trace
— terminal colour codes, which is why these are filed as info and never reach an error dashboard
12,000entries a day carrying the credential. 437 measured in a single 51-minute window. It has been there for as long as this code has shipped.

What we are asking for

1. Replace the interceptor with four structured fields. Two hours.
2. Rotate the secret. Treat it as leaked. It is shared with prod-ms-insurance.
3. Tell whoever owns security review.

Anyone with log read access in the production project has had this credential.

This was not what we were looking for. It is what you find when you read nine million log lines instead of counting them.

07/The Datadog position

We own more of Datadog than we use, and parts of it are broken

We audited every environment. The expensive half is already deployed and working. The cheap half is missing.

Already working, and better than our own documents claim

APM covers 42 production services — 79 million spans over two days, including database and queue spans. Most squads do not know this exists. Earlier packs said Bravo’s workflow layer produced no traces; prod-ms-bpm has over a million.

Logs and traces are not joined up

Zero logs carry a trace id. Nobody can click from a slow trace to the logs for that request, or from an error to the trace that caused it.

Only 30 of 71 services send both logs and traces. Two services have different names in logs and traces, so Datadog treats them as four.

Monitors that report OK and can never fire

A family of about twenty log monitors targets dev-, sit- and uat- services. No non-production logs reach Datadog at all, so none of them can ever trigger.

Worse, the production sharia monitors query prod-sharia-sharia-bpm-sharia — note the doubled word, a service that does not exist. They show OK because nothing matches, not because nothing is wrong.

Three more, briefly

8 synthetic tests, all DNS and SSL checks. Nothing tests whether a customer can submit a loan.

23 Dockerfiles download the tracer from releases/latest — unpinned, in production.

Production alerts route to @googlechat-test and @webhook-testwebhook.

08/The plan

The order matters, because Datadog bills on what we send it

The obvious move is to turn on the Datadog features now. That would make the bill worse.

The trap we nearly walked into

The fix for 16 KB line splitting is to have the Datadog agent rejoin the fragments. Correct — but applied to today’s stream it would faithfully reassemble the 64 KB request bodies and the credential-carrying error dumps into single large billable events, and index them.

We would pay Datadog premium rates to reconstruct exactly the content that should never have been logged.

Clean the stream first. Then enable, on half the volume, at half the recurring price.

The gate SRE holds before enabling anything

Production log lines / day
4.5M→under 2.5M

Protects the per-GB price of everything downstream. The five services on slide 06 are most of the gap.

Share Datadog can parse
6.4%→over 80%

The one people will want to skip. Datadog cost filters work on parsed attributes — on raw text they are guesswork, and will silently drop evidence we needed.

Squads first, SRE second

This is not a queue. The squad work is what makes the SRE work affordable, and it is already written up per repository — nineteen files, each naming the file and line to change.

09/The plan

Four phases. The money is in the first one.

Phase 1 · nowPlatform configuration and defect fixesNon-production exclusion filters and retention. Cloud SQL logs off in non-prod. Flow log sampling to 10%. Fix the dead monitors. Pin the tracer. Name an owner for the blank-line service.No Datadog cost · 2 weeks
Phase 2 · nextSquads cut log volumeNineteen per-repository guides, each naming the file and line. The five services on slide 06 are 64% of it. SRE holds the gate and tracks two numbers weekly.Reduces cost · 4–6 weeks
Phase 3 · gatedIngestion and correlationLine reassembly, trace correlation, per-service cost filters in the same change. Trace the API gateway, with sampling from day one.Small increase · 1 week
Phase 4 · one at a timePaid add-onsRuntime metrics, then database monitoring on ten services, then profiling on one. Real synthetic tests. SIT and UAT logs into Datadog — last, and errors only.Per product · measure each
Rp 81–105Ma month, recovered in Phase 1 alone. No code change, no squad backlog, no release.
2 wksto bank it. Phase 1 is platform configuration and one access review.

What we are deliberately not doing yet

Sending non-production logs to Datadog. It is the item most likely to blow the budget, and it is a convenience improvement with a real recurring cost. It comes last, restricted to SIT and UAT, errors only, three-day retention — and only after the savings are banked.

Coralogix stays an open question. Rp 253M a month, flat since February, and no document we hold explains what it is for. That answer may be worth more than everything else on this slide.
