01/Orientation

One Spring Boot service, one embedded engine, one database, every retail loan we write

A consumer-finance lender in Indonesia. ms-bpm takes a loan application from lead to go-live: survey, credit bureau, scoring, underwriting, approval, signing. It is the system of record for applications in flight.

135kloan applications started a month
541kapplications open right now, tail up to one year
53BPMN models and 3 DMN tables, all to become Java
272Java delegate classes behind 483 service tasks, future activities

Two generations of model, both in scope

Legacy, per product: five large flat processes (NDF4W, NDF2W, repeat-order, Sharia, unsecured) carry about 94% of volume and 78% of the BPMN by line. Unified: one spine that calls 32 child processes, one per domain step, where new products land. Product routing is a map in configuration, not a diagram decision.

What sits around the engine, and stays

About thirty microservices called from delegates. 238 JPA entities and 271 tables in PostgreSQL. Three in-house operator consoles (764,000 lines of React) that never see an engine task id. Keycloak for identity. All of it stays where it is; only the orchestration tier moves.

What this means

The unified spine is 37 files and 8,540 lines, with per-product variation already held as data in configuration tables rather than in the diagram. Porting it is a bounded job. The two legacy monoliths, ndf4w.bpmn and ndf2w.bpmn, are 46% of all BPMN on their own and hold 212 of the 384 escalation and link elements. They also use errors, not escalations, as the child-to-parent channel, so a direct port designs two return idioms.

Three orderings we want your view on

Direct: port everything. Consolidate first: move legacy products onto the unified spine inside Camunda, then port one spine; removes 78% of the BPMN from the port but migrates the biggest product twice. Spine first: port the spine as the pilot on about 5% of volume, then move each legacy product straight onto the Temporal spine, writing the long-tail activities once.

The one deep dependency

A delegate updates our JPA entities and the engine updates ACT_RU_* in the same PostgreSQL transaction. If the delegate throws, both roll back together. 260 asyncAfter boundaries were placed with that in mind. As activities, the database write and the activity completion are two operations, and every one of 483 activities needs to be safe to run again. We think most of it can live in one base activity class and an idempotency key. We want your view.

There is no drain window, and no instance migration tool

540,824 top-level applications are open. 408,638 started more than 90 days ago, 59,710 more than a year ago. Nothing moves a Camunda instance into a Temporal execution. So the shape is either route new applications to Temporal and let Camunda run off for a year, or reconstruct state and start matching executions. We want your view on both, and on what a workflow parked for a year costs in history.

07/Temporal at BFI today

We are not a new customer: a year of production in Go, and a Java pilot in review

8Go services on the Temporal Go SDK, versions 1.34 to 1.48, on our other origination platform
49kRunning executions in the production namespace; about 5,000 starts a day
22kpeak Running per version at a handover; one task queue per version
1.39Java Spring Boot starter in a sibling Bravo service: update-with-start, steps facade, typed failures

Five lessons we bring to the call

Worker memory is the sticky cache: 0.75 MB per cached workflow, one worker type OOM-killed until we sized it. Retry ceilings: a 60-second maximum interval turned one outage into thousands of retries an hour; now 15 minutes. Search attributes were never defined, so “which loans are stuck at survey” is answered from our database, not Temporal. Version retirement needed a runbook for orphaned children. Trace spans miss 30–70% of long-running completions; use Temporal’s own counts.

What the Java pilot already settled

One workflow type per loan product from a template with a router. Business rejections as non-retryable ApplicationFailure mapped to the exact HTTP error body the consoles expect. A 30-day Workflow.await for a document wait. Worker in-process with the API pods, dark unless a target is configured. gRPC and protobuf pinned ahead of the Google BOM. What it has not done: a workflow that lives for days with human waits, at 135,000 starts a month. That is the gap this assessment closes.

09/Constraints

What does not move, and what the port must not break

Regulated workloadAuditability and retention are floorsLoan origination records for a supervised lender. 90 days of process history is the minimum, queryable after the workflow closes, and decisions must stay explainable after the fact.
No drain windowCamunda runs alongside for a yearHalf a million open applications with a one-year tail. Two engines in production under any plan; the application tables are shared, so outcomes can be diffed in one database.
Endpoint contracts764,000 lines of console must not changeThe consoles call domain verbs and never see a task id. Preserving those contracts is a hard constraint of the port, and the consoles’ 829 tests become the boundary regression suite.
PlatformGoogle Cloud, Temporal Cloud SingaporeGKE, Cloud SQL PostgreSQL 16, Keycloak. Data residency for an Indonesian lender needs a current answer.
Two deploymentsConventional and ShariaSame code, separate databases and pipelines, separate regulatory treatment. One or two namespaces.
TeamJava squads, a Go team next doorDeep Camunda 7 habits, one Java pilot, a year of Go production experience to draw on, thin automated coverage at the process layer.

What we can share, and what we cannot

Can: all 53 BPMN and 3 DMN files under NDA, the Java pilot’s design notes, anonymised database statistics, read access to our existing namespaces, and a read-only walk-through of the code with an engineer. Cannot: production data, credentials, or customer records. Not in this package by choice: internal cost figures, our contract terms, and comparisons with other vendors. Those are a separate conversation.
