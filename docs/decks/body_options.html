01/The finding

Bravo is not approaching two end-of-support cliffs. It has gone over both.

And it sits on the last publicly available build of each stack — there is no further free patch to take.

ComponentBravo runsSupport ended
Camunda 7 Community Edition7.23.014 Oct 2025 — line closed, final artifact 7.24.0, GitHub repo archived, no security patches ever again
Spring Boot 3.5.x (OSS)3.5.16 — the final OSS patch, 25 Jun 202630 Jun 2026
Java 17 (Oracle premier)17, on distroless / Temurin30 Sep 2026 — 20 days
Camunda 7.23 (Enterprise maintenance)— no licence held —13 Oct 2026 — 33 days

1 · A supported destination exists, and it is cheap

The Apache-2.0 community forks — Operaton 2.1.4 and CIB seven 2.2.0 — run on Spring Boot 4, keep the ACT_ schema unchanged, accept the legacy camunda: BPMN namespace and ship automated migration recipes. What ended is Camunda’s stewardship, not the engine.

2 · The binding constraint is Spring Boot, not Camunda

Camunda 7.23’s starter will not run on Boot 4, and the coupling runs one way: moving to Boot 4 forces an engine decision; swapping the engine does not force Boot 4. So “upgrade Spring Boot first, decide about the engine later” is not available.

3 · There is no second line of defence

61 injected remote-code-execution process definitions sit in the production engine, one confirmed executed inside the prod pod. An engine with no patch channel and a reachable deployment endpoint is the worst combination on this list.

07/Decision B, framed

What each option optimises for — and what it leaves unanswered

Option 1 · upgrade in place

Disruption avoided — and now speed and cost as well

  • Changes nothing about how a single engineer or analyst works: no data migration, no paradigm change, no retraining, no new language
  • Preserves everything the comparison found Bravo genuinely does better: bounded and classified failure with a designed dead-letter path, relational fleet queries, durable reprocess generations, an analyst-readable BPMN model, commodity skills
  • Cheapest orchestration tier of the three at ≈Rp58M/month
  • What it does not do: address Bravo’s architecture — five monoliths, product identity in five places, four status vocabularies

Option 2 · Temporal

Permanence without paradigm change — and migration risk

  • The only option that removes the vendor dependency for good while keeping the imperative model the team already thinks in, on infrastructure BFI already owns and staffs
  • Parity can be argued element by element rather than demonstrated path by path; rollback lands on the same database
  • Process legibility is preserved and made verifiable by a generated-vs-intent diagram diff
  • Its weakness: it changes the engine and preserves the architecture exactly. If the real complaint is Bravo’s design, this does not answer it

Option 3 · LORA

One platform and one capability

  • Adding an automated step without editing an orchestration model is real, validated, and the clearest thing LORA does better
  • The only option that ends the two-platform estate — and it removes ≈Rp58M/month of prod orchestration cost
  • Reliability currently favours LORA: ≈0.13% manual-intervention against Bravo’s ≈0.44%
  • Its price: a paradigm change whose cost is documented, partly remediable, and currently unremediated

The measured half — why it is sharper than it looks

The seam LORA lacks is one Bravo is actively running: two squads (BLCS and LN), two Jira boards, three operator consoles and separate sprint regression, with zero cross-project links. Option 3’s organisational cost is therefore concrete — merge two working squads and re-cut them by product family — not an abstract constraint.

The fair summary

The objection is real, mostly remediable, and cheap to remediate relative to the migration — but it is unremediated today, and a decision that assumes it away will meet it at full strength during cutover.

It is a reason to sequence Option 3 carefully, and a legitimate reason to prefer Option 2 if the organisation values the current mental model highly. It is not, on this evidence, a reason to rule Option 3 out.

11/The one open sub-decision

Inside Option 1, one question is genuinely open — and it is not a technical one

The question that selects the fork

Is a contractual support agreement required for the workflow engine — and can one actually be purchased for a BFI entity?

Yes → CIB seven.  No → Operaton.

Why it is on the critical path

It is the only sub-decision that cannot be answered from the codebase, and CIB seven’s terms — length, service levels, pricing — are not published. If the answer may be yes, open that enquiry now rather than after the technical work is scoped.

Operaton 2.1.4

9× the commit volume, 52 contributors, Apache 2.0 with no paid tier. Maintained on rolling 6-month support lines; no legal entity yet, a non-profit is planned.

Choose it if community velocity matters more than a contract.

CIB seven 2.2.0

Company-backed (CIB software GmbH), two ex-Camunda core engineers, a cheaper migration — no 7.24 hop first, Cockpit webjar path unchanged. Paid support exists; terms undisclosed.

Choose it if Risk requires a counterparty.

Either way, this is a chosen dependency

Adopting a project with a 6-month support line will be scrutinised differently from inherited drift. Say so in the paper rather than letting it surface in review.

13/How to read the numbers

Estimation basis, and what is deliberately not measured

Basis

Effort is in engineer-months of a competent engineer already familiar with the codebase, including that engineer’s own testing but excluding UAT run by business users.

Option 1 is the exception: its figures come from the Bravo team’s own Camunda 7 Exit Plan in engineer-days for one engineer, explicitly excluding review, deployment soak and open-question fallout — 18–33 days build, reconciled here to ≈1–1.5 engineer-months, or 1.5–2.5 all-in. Its inventory counts were re-verified against the working tree and matched exactly; its day estimates carry the team’s own “medium” confidence.

Ranges are low-to-high, not confidence intervals. Rupiah applies an assumed Rp30–50M fully-loaded cost per engineer-month — substitute BFI’s rate card. USD converts at Rp16,800.

What is not measured, and would change the numbers

The five open questions, plus Temporal commitment headroom and the true Bravo/LORA application split — the billing sheet’s application counts are the least-verified numbers in the pack (Bravo’s engine meter reports ~120k process starts/month against the sheet’s 76,446). Option 3’s estimate additionally does not separate incremental cost from work already on LORA’s roadmap; the gap inventory is the workstream that would.
