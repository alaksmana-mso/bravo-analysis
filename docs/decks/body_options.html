01/The finding

Bravo is not approaching two end-of-support dates. It has passed both.

And it is running the last build either product will ever release for free. There is no further patch to take.

ComponentBravo runsSupport ended
Camunda 7 Community Edition7.23.014 Oct 2025 — the line is closed, the final release was 7.24.0, the GitHub repo is archived, and there will be no security patches ever again
Spring Boot 3.5.x (open source)3.5.16 — the last free patch, 25 Jun 202630 Jun 2026
Java 17 (Oracle premier support)17, on distroless and Temurin30 Sep 2026 — 20 days away
Camunda 7.23 (Enterprise maintenance)— we hold no licence —13 Oct 2026 — 33 days away

1 · There is somewhere supported to go, and it is cheap

Two community forks under the Apache 2.0 licence — Operaton 2.1.4 and CIB seven 2.2.0 — run on Spring Boot 4, leave the ACT_ database tables unchanged, still accept the old camunda: BPMN namespace, and ship automated migration scripts. What ended is Camunda’s ownership of the project, not the engine itself.

2 · Spring Boot forces the decision, not Camunda

Camunda 7.23 will not run on Spring Boot 4, and the dependency runs one way only. Moving to Boot 4 forces a decision about the engine; changing the engine does not force Boot 4. So “upgrade Spring Boot first and decide about the engine later” is not an option.

3 · There is no second line of defence

61 process definitions designed to run arbitrary code are sitting in the production engine, and one of them has been confirmed to run inside the production pod. An engine with no way to receive patches, and a deployment endpoint anyone can reach, is the worst combination on this list.

07/Decision B, framed

What each option is good at — and what it leaves unanswered

Option 1 · upgrade in place

Avoids disruption — and now it is the fastest and cheapest as well

  • Changes nothing about how an engineer or an analyst works. No data migration, no new way of building, no retraining, no new language
  • Keeps everything the comparison found Bravo genuinely does better: failures that are bounded and classified, with a designed place for the ones that cannot be handled; questions across all loans in SQL; a durable row for every reprocess attempt; a BPMN model an analyst can read; skills that are easy to hire
  • The cheapest workflow tier of the three, at about Rp58M a month
  • What it does not do: anything about Bravo’s architecture — five monoliths, the product identified in five places, four status vocabularies

Option 2 · Temporal

A permanent fix without changing how we build — and migration risk

  • The only option that removes the vendor dependency for good while keeping the step-by-step model the team already thinks in, on infrastructure BFI already owns and staffs
  • You can argue it matches Bravo element by element, rather than having to demonstrate every path. And a rollback lands on the same database
  • The workflow stays readable, and a diagram diff between what was generated and what was intended makes that checkable
  • Its weakness: it changes the engine and keeps the architecture exactly as it is. If the real complaint is Bravo’s design, this does not answer it

Option 3 · LORA

One platform, and one new capability

  • Adding an automated step without editing a workflow model is real, it is proven, and it is the clearest thing LORA does better
  • The only option that ends the two-platform estate — and it removes about Rp58M a month of production workflow cost
  • Reliability currently favours LORA: staff step in on about 0.13% of applications, against Bravo’s 0.44%
  • Its price: a change in how everyone builds, whose cost is documented, partly fixable, and not fixed yet

The measured half, and why it is sharper than it looks

The boundary LORA lacks is one Bravo is actively running: two squads (BLCS and LN), two Jira boards, three operator consoles and separate sprint regression, with no links at all between the two projects. So Option 3’s organisational cost is concrete: merge two working squads and re-cut them by product family. It is not an abstract constraint.

The fair summary

The objection is real, mostly fixable, and cheap to fix compared with the migration — but nothing has been fixed yet, and a decision that assumes it away will meet it at full strength during cutover.

It is a reason to sequence Option 3 carefully, and a legitimate reason to prefer Option 2 if the organisation values the current way of thinking highly. On this evidence it is not a reason to rule Option 3 out.

11/The one open sub-decision

Inside Option 1 one question is genuinely open, and it is not a technical one

The question that picks the fork

Do we need a support contract for the workflow engine — and can one actually be bought for a BFI entity?

Yes → CIB seven.  No → Operaton.

Why it is on the critical path

It is the only sub-decision we cannot answer from the codebase, and CIB seven’s terms — length, service levels, pricing — are not published. If the answer might be yes, open that enquiry now, rather than after the technical work has been scoped.

Operaton 2.1.4

Nine times the commit volume, 52 contributors, Apache 2.0, with no paid tier. Maintained on rolling 6-month support lines. There is no legal entity behind it yet; a non-profit is planned.

Choose it if an active community matters more than a contract.

CIB seven 2.2.0

Backed by a company (CIB software GmbH), with two ex-Camunda core engineers, and a cheaper migration — no need to go via 7.24 first, and the Cockpit webjar path is unchanged. Paid support exists, but the terms are undisclosed.

Choose it if Risk needs a counterparty.

Either way, this is a dependency we are choosing

Adopting a project with a 6-month support line will be judged differently from drift we inherited. Say so in the paper, rather than letting it come up in review.

13/How to read the numbers

How the estimates were made, and what we deliberately did not measure

How the effort is counted

Effort is in engineer-months of a competent engineer who already knows the codebase, including that engineer’s own testing but not UAT run by business users.

Option 1 is the exception. Its figures come from the Bravo team’s own Camunda 7 Exit Plan, in engineer-days for one engineer, and they explicitly exclude review, deployment soak and anything the open questions throw up — 18 to 33 days to build, which we have converted here to about 1 to 1.5 engineer-months, or 1.5 to 2.5 all in. We re-checked their inventory counts against the working tree and they matched exactly. The day estimates carry the team’s own confidence rating: “medium”.

Ranges are low to high. They are not confidence intervals. Rupiah figures assume a fully-loaded cost of Rp30–50M per engineer-month — substitute BFI’s own rate card. USD converts at Rp16,800.

What we did not measure, and what it would change

The five open questions, plus how much headroom the Temporal contract has, plus the true split of applications between Bravo and LORA. The billing sheet’s application counts are the least-verified numbers in the pack — Bravo’s engine reports about 120,000 process starts a month, against the sheet’s 76,446. Option 3’s estimate also does not separate new cost from work already on LORA’s roadmap. The gap inventory is the piece of work that would.
