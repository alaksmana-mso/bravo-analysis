01/Orientation

Who we are, in Datadog terms

A consumer-finance lender running a loan origination and servicing estate on GKE. Three languages, two shared wrapper libraries, one Datadog org, one two-year order.

~122production services on the cluster
71of them send logs or traces to Datadog today
3languages: Go (about two-thirds), Java Spring Boot, Node.js
2wrapper libraries every service imports — one Go, one Java

The wrappers are the lever

bfi-go-pkg gives every Go service its logger, HTTP middleware, gRPC interceptors and tracer setup. bravo-lib-logging (bfi-java-pkg) does the same for 18 Java services, and a new Spring Boot 3 starter in the same repository is taking that role for the 20 Java services already on Boot 3. A default changed in one of them reaches the whole estate in one release. Any workshop that ends with a wrapper change is worth more than thirty team sessions. We have two such changes in review now.

How we know what follows

Six weeks of review: 73 repositories read, production logs and spans queried in our org for every service, every production deployment manifest read, and the signed order Q-849776 (1 Oct 2025 – 30 Sep 2027) set against Datadog’s own estimated_usage metrics. Every number in this deck comes from one of those four places. Where a number needs your side to confirm it, we say so.

03/Logging

The log stream is large, mostly unparsed, and mostly avoidable

4.5Mproduction log lines a day
93.6%of them carry no parsed attributes — no @logger.name, no level, no trace id
64%of the volume comes from five services
16KBline split by the container runtime; every longer line arrives as fragments

Where it comes from

Request and response bodies logged at INFO. The Java wrapper defaults body logging to on; the Go wrapper is opt-in but eight production services have it on with an empty masking list. Eight services run production at debug. One service emits genuinely blank lines — 29% of everything. Serialised payloads, stack frames and the same error 20,000 times a day make up most of the rest. Almost none of it is a log a human wanted.

What we are doing about it ourselves

Forty-eight pull requests across the estate, three wrapper changes — including a new Spring Boot 3 logging starter that caps every Java line at 8 KB — and a manifest pull request with our SRE team. We hold ourselves to a gate before asking Datadog to ingest more: under 2.5M lines a day, over 80% parsed. The workshops on slide 10 are what get squads to keep it there — a team that can read a trace stops printing the payload.

04/APM

The traces are there. Almost nobody looks at them.

The expensive half of the product is deployed and working. The squads who would benefit do not know it exists, and the features built on top of it are untouched.

42production services covered by APM
79Mspans in two days, including database and queue spans
3M+spans a week from the workflow engine alone — controllers, JPA, outbound calls
12%of the committed indexed spans actually used

What is switched off, or never switched on

Error Tracking — derived from telemetry already flowing, costs nothing extra, not used. Database Monitoring — the Cloud SQL Postgres instances are not enrolled. Profiling — not enabled anywhere. Service Catalog ownership — empty. When an incident happens, engineers open logs, because logs are where they were taught to look.

The training gap this describes

Not “how to install the tracer” — it is installed. How a service owner reads their own service page, finds the failed request, follows it across five services and a database call, and answers the question without a single log line. Then how Error Tracking turns 20,000 identical errors a day into one issue with an owner.

05/Correlation

Logs and traces are not joined up anywhere

0production logs with a parsed @dd.trace_id, across two days
21services that emit dd.trace_id as plain text inside the message — injection is on, parsing is not
30 of 71services send both logs and traces; the rest send one or the other
8services carry a different service name in logs than in traces — Datadog treats each as two services

Why

No log pipeline parses our JSON, so dd.trace_id stays a string in the message. Unified service tagging is not applied on the pods, so names drift between the tracer and the log collector. And the 16 KB split turns the JSON of any long line into fragments no parser can read. Nobody can click from a slow trace to its logs, or from an error log to the trace that caused it. We own the feature and get none of it.

What we need to learn

Platform: pipelines and processors, trace-id remapping, reserved attributes, multi-line handling, unified service tagging on GKE. Squads: what their logger has to emit for the pipeline to work — MDC in Java, context loggers in Go — and how to check in the UI that it did.

06/Dynamic instrumentation

Squads log bodies because they cannot see them — and the feature that would fix that is blocked

Every squad we asked gave the same reason for logging request and response payloads: “Datadog does not show them.” They are right, and Live Debugger is the answer. It does not work in our org today.

Remote Configuration is failing

13 production services, about 91,000 failed polls a week, all with the same agent error: empty targets meta in director local store. Until it is fixed, no Live Debugger probe can be placed and no tracer setting can be changed from the UI. We have not found the cause on our side. This is the single item where we most need Datadog’s help.

Three things that limit what Live Debugger can do here

23 Dockerfiles download the tracer from releases/latest — unpinned, in production, so tracer behaviour changes without a deploy. Three services run on OpenTelemetry with dd-trace only indirectly, so they get no Datadog-native features at all. Node.js gets line probes only, and the Go estate — two-thirds of our services — is where dynamic instrumentation is thinnest.

If a squad can place a probe on a method and see the payload for one request, they will stop logging every payload for every request. That is the workshop with the largest effect on the ingestion line on slide 3.

07/Alerting, synthetics, RUM

Monitors that cannot fire, tests that test nothing, RUM half-configured

Monitors

About 20 log monitors target dev-, sit- and uat- services. No non-production logs reach Datadog, so they report OK forever. The production monitors for one product line query a service name that does not exist. 38 monitors match the workflow engine; none watches whether a loan is progressing. Alerts route to @googlechat-test and @webhook-testwebhook.

Synthetics

Eight tests, all DNS and SSL checks. Nothing exercises whether a customer can submit an application. A five-week production defect on the front end went unreported by monitoring while 2.4M front-end errors accumulated in RUM.

RUM

Two browser applications instrumented. One has allowedTracingUrls and joins browser sessions to backend traces; the other does not, and its sample rates were left at the defaults. Session Replay is bought (600K sessions a month) and, as far as we can tell, never watched.

The training gap

Monitors as code — Terraform or API, reviewed like software, routed to channels people read. Composite and workflow monitors that watch a business step, not a container. API synthetics that exercise a real submission. RUM setup done once, correctly, on both apps.
