The problem/Verdicts

Seven claims, checked against the build and against production

Business rules cannot be unit-tested properly

True

And for a sharper reason than in LORA. 776 of 1,457 files are plain Mockito tests, and Mockito can reach Java. But Bravo’s routing logic is not Java. It is conditionExpression strings inside 53 BPMN files, a six-column database selector, and a per-application on/off matrix in jsonb. All three are data, and no unit test runs any of them.

CI cannot tell an NDF4W underwriting change from an NDF2W one

True, and worse

The product is identified in five different places at once. And ndf2w.bpmn calls into the unified underwriting sub-process, so a change to unified underwriting reaches NDF2W — 248,685 applications over 90 days — with nothing in the build saying so.

Nothing is checked until the service is serving traffic

Confirmed

All 53 BPMN and 3 DMN files are deployed and read at Spring Boot startup. In 7 days the engine produced 38,198 ENGINE-09004 warnings in production, naming real modelling mistakes in real files. There is no check before that point.

“Still running” is treated as “healthy”

Confirmed, in Bravo’s own form

Here it is “not a 5xx” that gets treated as healthy. Every success-rate monitor filters on http.status_code:5*. A flood of 748,686 404s a week, across 69% of surveyor sessions, counts as a healthy service by that definition.

A nightly end-to-end run proves the contract

It exists — and it cannot fail

Corrected 2026-09-11. Bravo has a 595-file Cypress and Cucumber suite in a sibling repository, plus four CI workflows, one of them scheduled weekly. But every step ends with || true, so the run can never go red. It covers 10 of the 595 files. And the repository has been frozen since 2023-11-21. LORA’s nightly run is mostly red, which is bad. Bravo’s is permanently green by design, which is worse. Even if it ran: 57% of the Then steps in its 465 UI feature files only click and type. Its 130 API files do assert, on 87% of their steps, so the problem is confined to the UI half.

The 2,286-file suite is a safety net for the workflow

No

Four test files deploy and run a Camunda process, one of them against a production BPMN. Nothing tests what happens when retries run out, when an incident is raised, when an escalation crosses a callActivity, or when a loan is forcibly terminated.

There is a coverage gate

There is no gate

pom.xml sets JaCoCo to report and never to check, so there is no threshold. The makefile passes -Dspring-boot.run.profiles, which surefire ignores — so the tests are not running under the profile the build says they are.

The through-line

Bravo’s tests cover the Java they can reach. They do not touch the XML, the config tables or the engine — which is where a loan’s behaviour is actually decided. So the build can go green for a change that alters the routing of 94% of production volume.

One structural difference favours Bravo

Bravo has 2,286 test files across four repositories, against LORA’s 608 across 13. LORA has four repositories with no tests at all, and lora-process-sdk has no .github/workflows/ directory whatsoever. Every Bravo repository that is not frozen runs its tests on every pull request. Bravo’s problem is that it covers the wrong things; LORA’s is that some repositories are not covered at all. Corrected 2026-09-10 — this panel used to say “Bravo has one repository, one build”, which was false. There are four, and the corrected totals widen the gap in Bravo’s favour.

The giveaway

camunda-bpm-assert, camunda-bpm-process-test-coverage and camunda-bpm-mockito are all listed in pom.xml, and all three are effectively unused. Somebody knew this was the right way to test a BPMN system, added the dependencies, and the practice never caught on — the same shape as LORA’s lora-super-test, which has 150 scenario tests and nothing in CI to run them.

Sections 1 to 6 diagnose the problem. §7 is the proposed structure — nine layers ordered by cost, L0 to L8, a regression suite T1–T12, a failure suite N0–N12, and a rule that says which layer should have caught what.

§2/What we found

Where the business rules actually live, and why Mockito cannot reach them

In LORA we graded this complaint overstated, because LORA’s rules live in Go preconditions that PreConditionIsMet(nil, data) can run directly — 97 test files already do. In Bravo the complaint holds, because a large part of where decisions are made is not in Java at all.

Where a routing decision livesWhat form it takesCan a unit test run it?
BPMN gateway conditions — 137 exclusive gateways in ndf4w.bpmn aloneJUEL expressions inside XMLNo — only by deploying the process and running it. 4 test files do that
Which steps run for this applicationWorkflowProductConfig, then WorkflowMasterConfig, then a per-application matrix in jsonbNo — they are rows in PostgreSQL, shipped as Flyway data migrations
The skip check itselfBaseActivity.execute() reads the matrix, then either runs or does nothingYes in principle — but what is in the matrix is still data
Which BPMN process starts for a productA YAML map from productId to key at application.yaml:1364, with a Java override for ROPartly — and the map contains four keys that are not deployed processes
Approval chain rulesBaseUnderwritingApprovalServiceImpl, 4,604 lines, behind feature flagsYes — genuinely Java, and genuinely testable
Permanent error versus temporary one, and the decision to degrade50 customErrorHandle implementations, called on the last retryYes for the handler itself. No for “does the engine ever actually reach the last attempt”

Bravo’s Java is testable, and largely tested. Bravo’s decisions live in XML, YAML and database rows — and no test in the build runs any of those.

Why that is expensive

The customErrorHandle framework contains at least one credit-policy decision: after three failed attempts it skips anti-fraud, to keep the pipeline moving. Whether that path is ever reached depends on failedJobRetryTimeCycle, which is a string attribute on a BPMN element. There are 186 of them, with 30 different values, including 5 PT4M values that have no repeat count and so do not do what their author intended. No test checks that any step’s retry policy is what the modeller meant — and the one that skips anti-fraud is the one where being wrong is a credit-risk event rather than an outage.

A change to any one of these can alter the behaviour of one product, several, or all of them. Adding DF2W Sharia (product 15) touched all five, behind per-product feature flags.

Nothing connects a change to the products it affects

There is nothing in the build — no test name, no tag, no line in a coverage report — that says which products a given change reaches. A reviewer’s only tool is knowing all five mechanisms by heart.

LORA’s answer is structural, not tested

Product families have separate document schemas, separate workers and separate task queues, so a change to …/ndf2w simply cannot reach NDF4W. LORA still cannot tell you which product a shared-planner change affects — that is its own True verdict — but it has fewer ways to get it wrong.

§3/Reason two — the largest production exposure in the pack

The bridge from the old workflows into the new ones

ndf2w.bpmn calls into the unified underwriting sub-process. And no callActivity anywhere in the codebase sets camunda:calledElementBinding, so every child resolves to the newest deployed version at the moment it is called.

Now put those two facts next to the production volume split

A change to unified-underwriting-*.bpmn — the “new” generation, which carries 5.5% of volume — is picked up by NDF2W loans that are already running, at their next call. That is 73% of BFI’s origination volume, reached through a file whose name says it belongs to the other generation. There is no migration plan, no version pinned, and no test.

Nothing covers this path

The four Camunda-running test files do not cover it, and neither does anything else. This is the most consequential untested path in either platform, and it is invisible when you review the change.

§4/What we found

The models get checked in production, 38,198 times a week

The LORA complaint was that validation is “only JSON Schema, applied after the worker is already serving traffic”. Bravo has no schema registry at all, so the equivalent question is: when does anything check a process model? When the pod starts, in production. Spring Boot deploys every BPMN and DMN file it finds — there is no deployment-resource-pattern to narrow it — and the engine reads and versions each changed definition as it boots. That read is the only check there is.

A typical line, captured live

status:  warn
version: v2.93.53
message: ENGINE-09004 Warnings during parsing:
  * Exclusive Gateway 'Gateway_X_KYC_Verified' has
    outgoing sequence flow 'Flow_Condition_KYC_Verified'
    without condition which is not the default flow.
    We assume it to be the default flow, but it is bad
    modeling practice, better set the default flow in
    your gateway.
  | resource unified-kyc-check.bpmn
@activityName: KYC Check
@processDefinitionId: 544e3ea0-ab85-11f1-ba59-16deca89b476

Read that carefully. The engine is telling the team, in production, that a gateway on the KYC path has an outgoing route with no condition on it, and that Camunda is guessing this is the default. A routing decision is being settled by the engine’s assumption rather than by the model. The warning even names the file. It has been repeating across at least two deployed versions.

1 · Checked after deployment, not before

Every one of these warnings is available at build time. camunda-bpm-assert plus a parse test would surface them in seconds. Not one of them fails a build today.

2 · The count reflects how often pods restart

…and that is informative too. 38,198 in a week across two versions means pods are restarting often and re-reading all 53 files each time. The number of distinct warnings is small. The volume tells you about pod churn.

3 · Nothing reads them

No monitor matches ENGINE-09004. The warnings land in the same stream as the 525,181 error lines a week, and nobody sees them.

The honest comparison. LORA’s docFieldCheck crashes the worker at startup if a schema path is missing. That is late, but at least it is fatal and it happens on every deployment. Bravo’s equivalent check writes a warning, assumes a default, and serves traffic.

§5/What we found

“Not a 5xx” means healthy

Bravo does not have LORA’s failure mode

About half of LORA’s loans never reach a finished status, while producing no errors and no failed attempts — every signal reads healthy. Bravo’s BPMN checkpoints fail quickly, raise an incident and park the loan, so a stuck Bravo loan becomes a visible ticket rather than an invisible running workflow. That is a real advantage, and it is why Bravo’s stuck-application rate is measurable at about 0.44%, while LORA’s silent half went unnoticed for months.

This is an inference, not a fact

The last commit was 2023-11-21. GitHub turns off scheduled workflows after 60 days of repository inactivity, so the weekly job is very likely not running — and zero CI pipeline events in 30 days fits that. We cannot confirm it from a local checkout. Somebody has to open the Actions tab. Five minutes, and it is the first item in the plan.

§6.1/Added 2026-09-10

If the 349 surveyor files are being re-pointed, fix the writing style first

Re-pointing a file that names buttons, hard-codes waits and ends every Then with a click gives you a re-pointed file with the same defect. Eight rules, each answering a measured number — and the first four can be checked automatically in about 50 lines of code over a parsed Gherkin file.

RuleViolations
1. A Then may not contain an action verb. Then checks; When acts7,418
2. A scenario about a business rule may not name a UI element — no button, field, dropdown or page7,042
3. No wait in a step. Time appears only as an SLA or an expiry rule618
4. Use Scenario Outline only when Examples has at least 2 rows that change the outcome1,007 of 1,068
5. Feature: names a business capability, never whether the test is positive or negative463 of 595
6. One scenario, one rule. If the name needs “and”, split it97 run over 100 steps
7. Step text in English; Indonesian only inside quoted values1,349
8. A capped, reviewed list of step phrasings — the When list closed2,438 phrasings

Why a style check comes before the sorting

The suite decayed this way once already. 1,229 of its 2,438 step phrasings are used exactly once, behind 1,691 step definitions across 206 files — so the glue code is one-to-one with the prose, and every re-pointed file drags its own bespoke steps along with it. There is even a branch on the remote called B4WH-5851-qa-split-object-and-action: QA diagnosed this themselves, and the fix never landed.

Two tiers, and the ratio between them is the real fix

Many small scenarios that check a state, a status or a rejection reason. These belong at L3 to L5. And single digits of full UI journeys per product, at L7 to L8. Collapsing the two is how a scenario ends up 319 steps long, and a scenario that long cannot fail for one clear reason. Bravo’s own API features are the first tier done correctly — the model to copy is in the same repository.

Keep one thing exactly as it is

Every scenario carries a Zephyr key — @BLOS-T3424, @B4WH-T808 — under a @ProjectKey feature tag. It is the same scheme LORA enforces as @BL-T<n>. It links a requirement to a test run, and it is the one practice in this suite that needs no correction.

§7/The strategy

Sections 1 to 6 are the diagnosis. This is the structure.

The diagnosis on its own has a weakness: nine recommendations with no structure to hang them on become nine tickets, each argued separately. LORA’s lora-super-test does have a structure — five layers prefixed with _ (_whitebox, _canary, _contract, _widgets, _utility), a four-row cost budget, and a Zephyr tag on every case. It also says why: running everything end to end against SIT “tested their uptime, not our code”. Bravo has no equivalent structure at all. What follows is built from Bravo’s own decisions rather than copied from LORA.

Design rule 1 — from LORA, and still true here

Test only what you control, and own the answers at the boundary. LORA’s boundary is a single gateway envelope. Bravo’s is different, and it is better in one way and worse in another.

Design rule 2 — the whole point for Bravo

A change should fail in the cheapest layer that can see it. LORA states this as a rule of thumb. For Bravo it carries real weight, because Bravo’s expensive layer — a Camunda process test — is the only layer that exists for the workflow today, and it exists four times.

Where Bravo’s test boundary actually sits

LORABravo
Shape of a call to an upstreamOne envelope, POST /proxy/inner/request-v1, naming its schema113 typed @FeignClient interfaces, one per upstream
Where you intercept itOne mock, matching on api_data_schema, answers for about 300 upstreams113 sets of stubs — more of them, but each is a typed Java interface
What catches a stub drifting out of datecheck:stubs, run against the live LSS schema registryThe compiler. Bravo has no schema registry — but a stub built from the Feign type cannot drift without breaking the build
Can you make an upstream fail on demand?Yes, per run — a spec changes one answer in two linesNo. bravo-mock-service (Mockoon, at *.mock.bravo.bfi.co.id) is fixed and shared — the same weakness LORA names when explaining why it built its own

The finding is in the last two rows, and they point in opposite directions. Bravo’s boundary needs no schema registry to stay honest, because 113 typed interfaces are checked by javac, where LORA’s 300 JSON envelopes need a purpose-built script. That is a real advantage, and Bravo got it for free. But Bravo has no way to make an upstream fail on demand — and the failure suite is the list of what that costs.

This implies a different order from the recommendation list — and a better one

L0 and L1 should come first

Bravo cannot make an upstream fail at all. And Bravo’s version is the cheaper one to build

N0 to N12 need one piece of infrastructure, and it is the same piece LORA built: a per-run stub layer in front of the 113 Feign clients, where a test changes one answer and everything else comes from a shared baseline. Bravo’s stubs are generated from typed interfaces, so there is no schema registry to keep in step and no check:stubs script to write.

assertThat(application)
  .hasCreditDecision(BYPASS)

Five L6 journeys covers the whole product range: NDF2W, NDF4W, RO, unified DF4W and DF2W. Five tests would cover the normal path across 100% of production volume, against the zero that cover it today. They are the expensive layer, deliberately kept to five, because L0 to L4 catch everything that does not need the engine.

§7.6 · Three rules that stop it decaying

1 · No hand-written lists of what to expect

LORA works out its 24-stage plan from real traces, because hand-written lists “were proven wrong twice”. Bravo’s equivalent is the set of steps each product runs: derive it from act_hi_actinst, never type it out. This depends on the job-executor traces in bravo-observability.md rec 8 — without them, a derived Bravo expectation has nothing to derive from. That is the one dependency this document has on another.

2 · No selectors or field paths inside a test

Bravo’s version: no productId == 1L written into a test. A test asks the config layer which product it is, so that a test cannot become the sixth way the product is identified.

3 · No stub copied into a case

Name a baseline bundle and state only what differs. That is what makes N0 to N12 two lines each, instead of a fixture per case.

And one rule that is Bravo’s alone

A snapshot is never recorded automatically. LORA states the reason precisely: if the first passing run records the baseline, “that day’s form — bugs included — would silently become the truth”. For Bravo the trap is bigger, because L0 would otherwise record 38,198 parse warnings a week as the approved state of the models.
