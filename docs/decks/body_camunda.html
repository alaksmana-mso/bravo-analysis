01/Orientation

One Spring Boot service, one embedded engine, one database, every retail loan we write

A consumer-finance lender in Indonesia. ms-bpm takes a loan application from lead to go-live: survey, credit bureau, scoring, underwriting, approval, signing. It is the system of record for applications in flight.

135kloan applications started a month
541kapplications open right now, tail up to one year
53BPMN models and 3 DMN tables
272Java delegate classes behind 483 service tasks

Two generations of model, both in scope

Legacy, per product: five large flat processes (NDF4W, NDF2W, repeat-order, Sharia, unsecured) carry about 94% of volume. Unified: one spine that calls 32 child processes, one per domain step, where new products land. Product routing is a map in configuration, not a BPMN decision.

What sits around the engine

About thirty microservices called from delegates. Three in-house operator consoles (764,000 lines of React) that never see a Camunda task id. Cockpit, used by operations to retry failed jobs. Keycloak for identity. A second, separate Camunda 7.17 in another squad, out of scope here but relevant to any licence conversation.

03/Process models

What is in the 53 models, counted element by element

483service tasks, every one a delegateExpression to a Spring bean
96user tasks in 26 files; no forms, no candidate groups, no listeners
56call activities, all latest binding, all variables in and out
513exclusive gateways; 14 parallel; 4 inclusive; 2,214 sequence flows

Three patterns carry the models

Error end event to error boundary event on an enclosing sub-process: 104 ends, 106 boundaries, 114 error codes, thrown from 88 BpmnError sites in Java. Escalation end to escalation boundary for non-error outcomes such as “send back to surveyor”: 108 ends, 82 boundaries, 97 codes. Link events to keep big flat diagrams readable: 146 throw, 48 catch. 154 embedded sub-processes exist mostly as scopes for those boundaries.

What is not there

No script tasks, no send or receive tasks, no message or signal events, no multi-instance, no compensation, no execution or task listeners, no external-task topics, no connectors, no field injection, no tenants, no form keys. Timers are 12 fixed durations from 5 seconds to an hour. The surface is simpler than the file count suggests.

04/Expressions, human tasks, jobs

All JUEL, no FEEL; user tasks are wait states, not forms

659JUEL conditions on sequence flows; 109 call a Java method
78of them read Spring configuration with environment.getProperty(...) to switch flow on a feature flag
239input and output parameter mappings, mostly string literals
186failedJobRetryTimeCycle declarations, 31 distinct back-off patterns; 260 asyncAfter

How a human task actually works here

Our console shows the work and calls a domain endpoint on ms-bpm. The service finds the task by process instance and task key, then calls TaskService.complete. 48 complete sites, 24 claim sites. Assignment comes from a variable (#{surveyAssignee}, 21 tasks). Tasklist and Camunda Forms are not used. We need the wait state and an API, not a UI.

The expression pattern with no obvious Camunda 8 home

Reading a Spring bean inside a gateway condition works only because the engine lives in our JVM. 78 conditions do it. Turning every flag into a process variable on every instance is the naive fix. We would like your recommended pattern before we count effort.

The one deep dependency

A delegate updates our JPA entities and the engine updates ACT_RU_* in the same PostgreSQL transaction. If the delegate throws, both roll back together. 260 asyncAfter boundaries were placed with that in mind. In a job-worker model those become two operations, and every one of 483 tasks needs an idempotency answer. We think most of it can live in one base worker class. We want your view.

09/Constraints on both paths

What does not move, whichever path we take

Regulated workloadAuditability and retention are floorsLoan origination records for a supervised lender. 90 days of process history is the minimum we keep, and decisions must stay explainable after the fact.
No drain windowIn-flight state is the plan, not a footnoteHalf a million open applications with a one-year tail. Every deployment today is already a hot deployment against live engine state.
Human work is oursThree consoles, zero Camunda referencesThe operator experience is built and will not be rebuilt on Tasklist. The engine must expose the wait state and an API. That is all the UI tier asks of it.
PlatformGoogle Cloud, IndonesiaGKE, Cloud SQL PostgreSQL 16, Keycloak. Data residency matters for any SaaS answer.
Two deploymentsConventional and ShariaSame code, separate databases and pipelines, separate regulatory treatment.
TeamJava and Spring squadsDeep Camunda 7 habits, no Camunda 8 or Zeebe experience, thin automated coverage at the process layer.

What we can share, and what we cannot

Can: all 53 BPMN and 3 DMN files under NDA, anonymised database statistics beyond the ones in this package, and a read-only walk-through of the code with an engineer. Cannot: production data, credentials, hostnames, or customer records. Not in this package by choice: internal cost figures and vendor comparisons. Those are a separate conversation.
