01/Orientation

One Spring Boot service, one embedded engine, one database, every retail loan we write

A consumer-finance lender in Indonesia. ms-bpm takes a loan application from lead to go-live: survey, credit bureau, scoring, underwriting, approval, signing. It is the system of record for applications in flight.

135kloan applications started a month
541kapplications open right now, tail up to one year
53BPMN models and 3 DMN tables on the main line
272Java delegate classes behind 483 service tasks

Why a fork is on our list

Our models, our delegates and our data all assume an embedded Camunda 7 engine sharing one transaction with our application tables. A fork that keeps the engine, the ACT_* schema and the camunda: namespace could take us to a supported stack without touching any of that. We want to know whether CIB seven is that fork, and on what support terms.

What sits around the engine

About thirty microservices called from delegates. Three in-house operator consoles (764,000 lines of React) that never see a Camunda task id, so an engine swap changes none of them. Cockpit, used by operations to retry failed jobs. Keycloak for identity.

03/Process models

Nothing to convert, everything to reproduce exactly

483service tasks, every one a delegateExpression to a Spring bean
659JUEL conditions; 78 call a Spring bean with environment.getProperty
186retry cycles with custom back-off; 260 asyncAfter boundaries
56call activities, all latest binding, all variables in and out

The behaviours we most need unchanged

Job retries and incidents on exhaustion. Error propagation: 104 error ends to 106 error boundaries, thrown from 88 BpmnError sites. Escalation: 108 ends to 82 boundaries. JUEL with Spring bean calls and execution.hasVariable. Call activities picking up new versions under running parents. 4 inclusive joins and 194 link events.

What is not there

No script tasks, message or signal events, multi-instance, compensation, listeners, external tasks, connectors, tenants or form keys. 3 small DMN tables. The models use only standard Camunda 7 semantics. The question is behavioural equality with 7.23, not conversion.

The one deep dependency, which a fork keeps

A delegate updates our JPA entities and the engine updates ACT_RU_* in the same PostgreSQL transaction. If the delegate throws, both roll back together. Our 260 asyncAfter boundaries rely on it. Keeping this model is the main reason a fork is on our list. We want you to confirm nothing in CIB seven changes it.

09/Constraints

What does not move, whichever route we take

Regulated workloadAuditability and patching are requirementsLoan origination records for a supervised lender. 90 days of process history is a floor. A published engine vulnerability has to be patched within weeks, not at the next six-monthly release.
No drain windowIn-flight state resumes in placeHalf a million open applications with a one-year tail. Every deployment today is already a hot deployment against live engine state.
Keep what worksSame models, same transaction, same consolesThe value of a fork to us is that the models, the shared transaction and the three consoles stay exactly as they are.
PlatformGoogle Cloud, IndonesiaGKE, Cloud SQL PostgreSQL 16, Java 17, Keycloak.
Two linesMain on 7.23, Sharia on 7.17Separate branches, databases and pipelines.
TeamJava and Spring squadsDeep Camunda 7 habits; thin automated coverage at the process layer.

What we can share, and what we cannot

Can: all BPMN and DMN files under NDA, further anonymised database statistics, and a code walk-through with an engineer. Cannot: production data, credentials, hostnames, or customer records. Not in this package by choice: internal cost figures and comparisons between vendors.
